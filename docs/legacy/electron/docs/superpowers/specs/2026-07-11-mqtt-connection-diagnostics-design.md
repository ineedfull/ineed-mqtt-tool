# MQTT Connection Diagnostics and Cancellation Design

## Goal

Make MQTT connection failures diagnosable without flooding the log, and let users cancel an initial connection attempt or an automatic reconnect cycle. Electron and Tauri must expose the same behavior and log semantics.

## Scope

- Distinguish initial connection, connected, reconnecting, disconnected, and error behavior.
- Allow the user to cancel initial connection and stop automatic reconnect.
- Classify disconnect causes and retain the original runtime error.
- Deduplicate the multiple low-level events generated by one disconnect cycle.
- Record reconnect attempt count, outage duration, and restored subscription count.
- Keep the top status display concise; detailed diagnostics belong in the log.

Active DNS/TCP/TLS probing is out of scope. A transport close cannot always prove whether the broker, network, or operating system caused it, so uncertain cases must be labelled as remote-or-network failures.

## Connection State Model

The renderer uses the following public status values, adding `reconnecting` to the existing model:

- `disconnected`: no active connection task.
- `connecting`: an initial connection attempt is in progress.
- `connected`: MQTT CONNACK has been received.
- `reconnecting`: a previously connected session is retrying after an unexpected interruption.
- `error`: the initial connection failed or a non-recoverable error occurred.

`connecting` and `reconnecting` are deliberately separate. The UI may still use the same warning color, but their labels and available commands differ.

## Status Event Contract

Both native runtimes emit the same status payload:

```text
connId: string
status: disconnected | connecting | connected | reconnecting | error
source: user | client | broker | network | unknown
code: stable diagnostic code
reason: original runtime or broker message
reconnected: boolean
attempt: number
disconnectedAt: millisecond timestamp or null
```

Stable codes include:

- `USER_CANCELLED`
- `USER_DISCONNECTED`
- `INVALID_CONFIG`
- `DNS_FAILED`
- `AUTH_FAILED`
- `BROKER_REJECTED`
- `BROKER_DISCONNECT`
- `KEEPALIVE_TIMEOUT`
- `CONNECTION_TIMEOUT`
- `CONNECTION_RESET`
- `SOCKET_CLOSED`
- `TLS_FAILED`
- `CLIENT_ERROR`
- `UNKNOWN_DISCONNECT`

Classification is conservative. Only an explicit MQTT response is attributed to the broker. Socket closure and reset without a broker reason are classified as `network` with wording that covers a remote or network interruption.

## Runtime Responsibilities

Electron's mqtt.js runtime and Tauri's Rust runtime each own their connection lifecycle. Each connection has exactly one current generation/token. Starting a connection or explicitly stopping it invalidates the previous generation. Events from an obsolete generation are ignored.

Initial connection behavior:

- Emit `connecting` once.
- Do not run indefinitely after the initial connection timeout.
- On success, emit `connected`.
- On failure, emit one classified `error` event and stop.
- On cancellation, close the client/task, emit `disconnected` with `USER_CANCELLED`, and prevent stale callbacks from changing state.

Reconnect behavior:

- Begins only after the connection has succeeded at least once and automatic reconnect is enabled.
- Emit one primary `reconnecting` event when an outage cycle begins.
- Increment `attempt` for each retry without generating repeated warning logs.
- On success, emit `connected` with `reconnected: true`.
- On stop, close the client/task and emit `disconnected` with `USER_CANCELLED`.
- Automatic reconnect does not restart until the user explicitly connects again.

## UI Behavior

The status button changes by lifecycle state:

- `disconnected` or `error`: `连接`
- `connecting`: `终止`
- `reconnecting`: `停止重连`
- `connected`: `断开`

All stop actions use the existing disconnect command boundary. The runtime decides whether the action means cancel initial connection, stop reconnect, or disconnect an active session.

Connection list indicators keep the existing colors. `reconnecting` uses the same warning color as `connecting`, with a distinct accessible label.

## Logging

The renderer converts structured status events into consistent logs.

Primary entries:

```text
INFO  开始连接 broker.example.com:1883
WARN  连接中断 [网络] ECONNRESET: Connection reset by peer，正在自动重连
ERROR 首次连接失败 [Broker] Not authorized
INFO  用户终止了连接
INFO  用户停止自动重连，已尝试 6 次，持续 18.420 秒
INFO  自动重连成功，断线持续 18.420 秒，正在恢复 8 个订阅
INFO  已恢复 8 个订阅，失败 0 个
```

Low-level events such as mqtt.js `offline`, `close`, and `reconnect`, or Rust event-loop poll errors, are retained as Debug entries. One outage cycle produces at most one Warn entry. Repeated retry failures update the structured attempt state instead of appending Warn entries.

## Subscription Recovery

Subscriptions are restored only after a reconnect receives CONNACK. Recovery reports total, success, covered, and failed counts. Cancelling a connection clears pending subscription timers and leaves saved subscriptions inactive.

## Error Handling

- Cancellation is an expected Info event, not an Error.
- A failed initial connection ends in `error`; it does not retry forever.
- An unexpected interruption after a successful connection enters `reconnecting` only when automatic reconnect is enabled.
- With automatic reconnect disabled, an unexpected interruption ends in `error` with its classified cause.
- Event ordering must not allow an old connection task to overwrite a newer connection's status.

## Verification

Automated tests cover:

- Initial connection cancellation.
- Reconnect cancellation.
- Stale generation events are ignored.
- Initial failure does not continuously reconnect.
- A post-CONNACK interruption enters reconnecting.
- One outage cycle produces one warning.
- Diagnostic classification preserves the original error.
- Reconnect success reports attempt count, duration, and subscription recovery totals.
- Electron and Tauri expose the same renderer event contract and button states.

Manual verification covers initial cancellation, stopping a live reconnect cycle, reconnect success, and log output in both desktop clients.
